# 编译跟踪与缓存实验

所有命令在项目根目录运行。运行时使用项目自身编译器、页管理器和缓存，不依赖外部数据库。

## 1. 表达式复杂度限制

WHERE 中的左括号与运算符总数最多为 64。运算符包括 NOT、AND、OR、比较、加减以及负数字面量前的减号。
括号闭合符、字符串内容、注释内容及标识符长度不计入；这约束结构复杂度，而不是字符串字数。
例如 `id > 18` 成本为 1，`NOT (id > 18)` 成本为 3。限制按单条语句独立计算。

Parser 在递归构建表达式前检查预算，超限时报告 syntax:EXPRESSION_TOO_COMPLEX，位置指向第 65 个结构 Token，并提示 SIMPLER_EXPRESSION。
预算同时限制嵌套括号、连续 NOT 与左深二元树，保护后续语义分析、优化、执行和 JSON 序列化。
超限且缺少闭合括号时优先报告复杂度错误；未超限的缺括号仍报告期望 `)`。
CLI 不退出崩溃；文件模式报错返回 1，交互模式可继续输入。显式事务中的错误仍须 ROLLBACK。

## 2. 输出完整编译过程

```powershell
.\.venv\Scripts\python.exe -m minisql --data-dir .\data\trace-demo --file .\examples\trace.sql --trace
```

`--trace` 执行真实 SQL，并输出 JSON Lines：标准输出每行一个 JSON 对象，错误信息仍在标准错误。
它不是只读 EXPLAIN；建表和写入会正常执行。示例将操作包在事务中，最后 ROLLBACK，便于重复演示。
使用普通 SQL 文件时，自动提交及显式事务行为与原 CLI 相同。

成功编译产生 `event: compilation`，字段依次为：

| 字段 | 内容 |
|---|---|
| tokens | 种别、原始词素及行列，包含 EOF |
| ast | 原始 AST，保留源码位置 |
| semantic | 语义检查通过后的绑定语句及表结构；事务语句的 schema 为 null |
| plan | 优化前计划 |
| optimized_plan | 优化后计划 |

每个 dataclass 对象带 `node` 字段标明类型；枚举转为字符串，元组转为 JSON 数组，中文保持原文。
示例查询的原计划含 `1=1 AND id>10+8`，优化后谓词为 `id>18`，仍保留 Project→Filter→SeqScan 结构。
控制语句显示 TransactionStmt 和 TransactionControl。序列化不修改原对象，也不额外编译或执行一次 SQL。

当前输入批次全部执行成功后，依次输出 `event: execution`，result 包含结果列、记录、受影响行数和提示。
compilation 只表示编译成功，不代表执行或提交成功。遇到后续错误时，可能已有编译事件，但该批次没有 execution 事件；这是 execute 原有的不返回部分结果约定。
失败语句的完整 compilation 对象不会输出，诊断查看标准错误。交互跟踪不打印提示符，便于程序逐行解析。

## 3. LRU/FIFO 缓存实验

```powershell
.\.venv\Scripts\python.exe -m minisql.cli.cache_experiment --capacities 2 3 4 --rounds 3
```

输出一个 JSON 报告，每个容量均运行 LRU 和 FIFO，并比较两种缓存生命周期。
默认每轮访问序列为 `1 2 1 3 1 2 4 1 2 3`，访问页 1、2 时修改其计数器，其余只读。
每种组合都使用相同的初始内容、相同访问序列及空缓存，避免前一个实验影响下一个。

```powershell
# 自定义序列，只读（--write-pages 后不提供页标签）
.\.venv\Scripts\python.exe -m minisql.cli.cache_experiment --capacities 2 3 --accesses 1 2 1 3 1 --rounds 2 --write-pages

# 混合读写，访问页 1 时修改
.\.venv\Scripts\python.exe -m minisql.cli.cache_experiment --capacities 1 2 --accesses 1 2 1 --rounds 1 --write-pages 1
```

实验默认在当前目录创建独立临时目录，结束时自动清理；可用 `--work-dir` 指定其他已存在的父目录。
不打开 data/ 下的已有数据库。访问标签和缓存容量必须为正整数，轮数必须大于零，写入页必须出现在访问序列中。

| 输出 | 口径 |
|---|---|
| hits / misses | 调用 get_page 时的命中/缺失次数 |
| evictions | 完成淘汰的页数 |
| writebacks | 成功写回脏页次数，含淘汰写回及轮末主动刷新，不是 fsync 次数 |
| hit_rate | hits / (hits + misses) |
| rounds | 每轮增量统计，不是累计值 |
| replacement_log | 每次淘汰的轮次、页标签、是否脏页及策略 |
| reopen_verified | 用新的文件实例重开验证写入内容是否正确 |

每轮都刷新脏页并同步文件；`continuous` 下一轮继续使用同一缓存，体现热缓存；`reset-per-round` 下一轮新建缓存，体现冷缓存。
后者模拟当前数据库每个新事务重建缓存的生命周期，但实验本身不执行 SQL 或事务，也不包括 Catalog、日志、建页或重开校验开销。
这是应用层页缓存实验，不是操作系统文件缓存命中率、磁盘物理 I/O 测量或 SQL 吞吐量基准。不能据此声称所有工作负载下 LRU 都优于 FIFO。

可人工核对的例子：只读序列 `1 2 1 3 1`、容量 2、每轮冷缓存时，LRU 每轮 2 次命中/3 次缺失，FIFO 每轮 1 次命中/4 次缺失。
容量 3 时，持续缓存第二轮没有缺失，而每轮重建缓存第二轮仍有 3 次缺失。
混合序列 `1 2 1` 只修改页 1 时，容量 1 写回两次，容量 2 在轮末合并写回一次；所有组合均重开验证数据。
