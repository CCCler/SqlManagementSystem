# MiniSQL 架构设计

## 设计依据与范围

依据《大型平台软件设计实习》指导书、总体 PPT 与 SQL 编译器专项 PPT。
指导书要求完成 SQL 编译器、页式存储和可交互数据库，至少执行 CREATE TABLE、INSERT、SELECT、DELETE，
表数据与 Catalog 都必须经页式存储持久化。专项 PPT 补充 AST、可定位错误、计划优化及验收要求。

本次只提供协作骨架、共享接口、测试替身、文档与帮助入口。所有业务实现待完成。
后续基础范围包括 INT/VARCHAR、内部 BOOL、比较和布尔表达式；进阶完成常量折叠和布尔化简。
JOIN、GROUP BY、索引、事务、并发控制和崩溃恢复不属于第一版。

## 分层与依赖

| 层 | 职责 | 允许依赖 |
|---|---|---|
| contracts | 类型、AST、计划、错误、Protocol | 标准库 |
| compiler | 切词、解析、语义、计划、优化 | contracts、编译器内部 |
| storage | 文件、页、缓冲池、记录存储 | contracts、存储内部 |
| engine | Catalog、算子、生命周期、装配 | contracts、compiler、storage |
| cli | 参数、交互、输出 | engine、contracts |

执行入口先切分语句，然后对每条语句依次编译、执行、刷新。
不能先对整个文件做语义检查：前一条 CREATE TABLE 必须先执行，后一条 INSERT 才能解析新表。

数据流：

```text
CLI → Database → SQLCompiler → AST / Semantic / Plan / OptimizedPlan
             ↓                         ↑
        PlanExecutor ←─────────────── Plan
             ↓                         ↑
        HeapStorage ← PersistentCatalog（编译器只读查询）
             ↓
        PageBufferPool → DiskPageManager → FileManager → 磁盘
```

## 关键边界

- 编译器不创建物理表，不修改 Catalog；名字解析通过 CatalogReader。
- 成员二统一负责 Row ↔ Page，包括编码、槽目录、空闲空间和表页映射。
- 成员三处理算子和元数据。SeqScan/Filter 保留 StoredRecord 的 RecordId；
  SELECT 的 Project 产生结果列，DELETE 只接收扫描或过滤结果。
- AST 和 Plan 是不可变 dataclass；优化生成新计划，以便展示优化前后差异。
- 分析成功返回 SemanticResult，失败抛出 MiniSQLError；NotImplementedError 仅表示开发占位。

## 持久化与启动

默认页大小 4096 字节，缓存容量 64 页，默认 LRU，可切换 FIFO。
存储模块持久化页分配信息和 table_id 到数据页的映射；业务代码不依赖其磁盘格式。
INT 使用有符号 64 位整数，VARCHAR 使用 UTF-8 长度前缀编码；超单页记录第一版明确拒绝。

table_id=0 保留给 __catalog；其结构固定在 engine/catalog.py。
新库通过存储接口创建系统表；重启时通过固定结构直接读取系统表，不经过 SQL 编译。
系统表记录 table_id、表名、列序号、列名和列类型，用户表编号从 1 开始。
引擎先创建物理表取得 table_id，再注册目录，每条成功写操作后 flush；正常 close 再刷新。
第一版保证正常关闭/重启的持久性，不承诺断电原子性；失败后的部分写入不当成事务回滚。

## 联调策略

成员一用 MemoryCatalog，成员二用固定 TableSchema，成员三用人工计划和 MemoryStorage。
先对齐契约，再联调 CREATE/INSERT/SELECT，随后 DELETE、错误、重启持久化，最后优化和统计。
测试替身没有页式存储能力，不能替代真实存储验收。
