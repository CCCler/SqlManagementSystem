# 增量日志改造方案（成员二 · 存储层）

> 现状：`storage/journal.py` 采用「完整文件前映像日志」，事务开始时把整个
> `minisql.db` 读入内存并复制到日志文件。本方案将其改造为「页级增量日志」，
> 只记录事务中真正被修改的页的前映像。

## 1. 现状与问题

当前 `RollbackJournal` 的流程（`database.py` 中 `_start`）：

```python
self._journal.recover()   # 启动恢复
self._journal.begin()     # 读整个 minisql.db 作为前映像，复制到 minisql.journal
self._reload()            # 之后的所有写入才发生
```

`begin()` 内部（`journal.py:104`）：

```python
before = self.database.read_bytes() if self.database.exists() else b""
with open(self.temp, "wb") as stream:
    stream.write(HEADER.pack(MAGIC, len(before), hashlib.sha256(before).digest()))
    stream.write(before)
```

问题：

1. **内存**：BEGIN 时把整个数据库读入内存，内存占用与数据库大小成正比。
2. **磁盘**：日志文件等于整个数据库的副本，空间翻倍。
3. **耗时**：BEGIN 的复制与 sha256 校验成本随数据库线性增长。

对教学规模可接受，但数据量增大后不可扩展。

## 2. 目标

- BEGIN 只建立空日志文件，不再复制整个数据库。
- 事务内，仅当某个页**第一次**被写盘前，记录该页的磁盘前映像。
- 提交/回滚/崩溃恢复语义保持不变；回滚能正确撤销新增页与修改页。

## 3. 关键前提（已核实）

- 所有写盘最终汇聚到唯一出口 `DiskPageManager.write_page`
  （`page.py:188`），调用方：`buffer.flush_page`、`buffer._evict_one`、
  `HeapStorage`、`DiskPageManager` 自身。
- `allocate_page` 分配新页时会更新页 0 的 `next_page_id`（`page.py:165`），
  因此**页 0 一定会在分配新页时被修改**，其前映像会进入日志。

## 4. 改造设计

### 4.1 日志格式（页级）

```
偏移 0..15    HEADER：MAGIC(8B) + 事务前 next_page_id(Q) 预留
偏移 16..     若干条 [page_id(I) + before_image(4096B)]
末尾          COMMITTED 提交标记（与原实现一致）
```

- `next_page_id` 用于回滚时把文件截断到事务前大小（撤销新增页）。
- 每条记录定长（`4 + PAGE_SIZE`），便于顺序追加与顺序恢复。
- 同一页只记录一次前映像（幂等，见 4.2）。

### 4.2 写盘前拦截（增量记录）

在 `DiskPageManager` 增加一个可选的事务日志引用，并在 `write_page` 写盘前拦截：

```python
def write_page(self, page_id: int, data: bytes) -> None:
    if self.journal is not None and self.journal.active:
        self.journal.log_page(page_id, self.files.read_at(page_id * self.page_size,
                                                          self.page_size))
    self.files.write_at(page_id * self.page_size, data)
```

`RollbackJournal.log_page(page_id, before)` 内部维护 `logged: set[int]`：

```python
def log_page(self, page_id, before):
    if page_id in self.logged:
        return                      # 同一页多次 flush 只记录首次前映像
    self._append_record(page_id, before)
    self.logged.add(page_id)
```

要点：

- 因 `begin()` 时文件仍是旧状态，且每页只在第一次写盘时记录，磁盘当前内容
  即为该页的**事务前映像**，`read_at` 得到的是正确前映像。
- 前映像写入日志后必须先 `fsync` 再写数据页，保证崩溃时前映像已落盘
  （与现有「数据先 sync、后写提交标记」的顺序原则一致）。

### 4.3 事务生命周期（改动点）

| 阶段 | 现状 | 改造后 |
|---|---|---|
| `begin()` | 读整个文件做前映像 | 仅建日志文件 + 写 header，`logged` 置空 |
| 执行写入 | buffer 脏页，flush 时写盘 | 写盘前经 `log_page` 记录该页前映像 |
| `commit()` | flush+sync 后写提交标记 | 不变：flush+sync 后写 COMMITTED |
| `rollback()` | 用整个前映像覆盖文件 | 按记录逐页恢复前映像，再截断文件 |
| `recover()` | 同上 | 未提交则逐页恢复 + 截断 |

### 4.4 回滚与新增页撤销

回滚时不能只恢复已记录的页，还要撤销「事务内新增的页」：

1. 从日志 header 读出事务前 `next_page_id = N_old`。
2. 按日志记录逐页写回前映像（含页 0，恢复其 `next_page_id` 为 N_old）。
3. `file.truncate(N_old * PAGE_SIZE)`，把新增页所在的空间截掉。

页 0 的前映像一定在日志中（分配页会改页 0），因此恢复页 0 后 `next_page_id`
与文件大小重新一致，空闲页链表等元信息也随之还原。

## 5. 涉及文件与改动点

| 文件 | 改动 |
|---|---|
| `storage/journal.py` | `begin()` 改为建空日志；新增 `log_page()` 与 `logged` 集合；`rollback/recover` 改为页级恢复 + 截断；header 增加 `next_page_id` |
| `storage/page.py` | `DiskPageManager` 增加可选 `journal` 引用；`write_page` 写盘前调用 `log_page` |
| `engine/database.py` | `_reload()` 中把 `self._journal` 传给 `DiskPageManager`；`begin/commit/rollback` 的调用顺序保持不变 |
| `tests/storage/` | 新增页级日志专项：修改页回滚、新增页截断、同页多次 flush 只记一次、恢复中再次中断 |

## 6. 兼容性与边界

- **对外接口不变**：`RecordStorage` / `PageManager` 协议签名不变，仅
  `DiskPageManager` 构造增加可选参数，默认 `None`（无日志）保持单元测试隔离。
- **崩溃边界**：前映像先 fsync 再写数据页；提交标记仍是唯一提交决定；恢复
  读取到未提交日志时逐页回放并截断，恢复中断可重试（与原实现一致）。
- **锁语义不变**：数据库级独占锁、自动提交、显式事务、退出回滚逻辑均复用
  现有 `TransactionalDatabase`。

## 7. 收益与代价

| 维度 | 完整前映像（现状） | 页级增量（改造后） |
|---|---|---|
| BEGIN 内存 | O(数据库大小) | O(1) |
| 日志磁盘 | 整个数据库副本 | 仅变更页 |
| 写盘额外 IO | 无 | 每页首次写盘前多读一次旧页 |
| 实现复杂度 | 低 | 中（需处理新增页截断与幂等） |

代价是每页首次写盘前多一次读（通常命中操作系统页缓存，实际开销可控），
换来 BEGIN 成本与日志体积不再随数据库大小增长。

## 8. 实施顺序（建议）

1. 先改 `journal.py` 的日志格式与 `begin/log_page/rollback/recover`，用独立
   单元测试验证页级回放与截断。
2. 再在 `page.py` 注入 journal 引用并拦截 `write_page`。
3. 在 `database.py` 接线，跑通现有事务与恢复集成测试（24 + 18 项）。
4. 补充新增页截断、同页多次 flush 等专项测试后，再评估是否替换默认路径。
