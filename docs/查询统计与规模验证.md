# 真实 SQL 查询统计与规模验证

> 本文为早期顺序扫描阶段实验。2026-09-12 已补齐索引直接回表；当前真实 SQL 的扫描/索引对比、计数范围及原始结果见[最终验收报告](最终验收报告.md)。旧表格的耗时与页数只代表当时版本。

测量脚本：`examples/benchmark.py`（`python examples/benchmark.py`），
测量函数：`minisql.cli.benchmark`（`measure_query` / `measure_executor`）。

## 测量环境与计数范围

- 真实页存储（4KB 页、64 页 LRU 缓冲池）+ 真实文件，每个规模使用独立数据目录，
  测量前关闭连接、测量时重新打开；不使用内存替身，也不把缓存重放实验当作 SQL 性能证据。
- 耗时数字受本机负载影响，仅用于数量级对比；扫描行数与页访问是可复现的权威口径。
- 计数范围（仅统计被测量的单条语句）：
  - 扫描行：存储 scan 接口返回的记录数（含被 Filter 过滤掉的），系统目录表读取不计入；
  - 页访问：当前活跃缓冲池的命中/缺失累计值。自动提交模式每条语句重建缓冲池，
    单条语句的值即该语句的页访问；同一显式事务内取两次测量差值得到单次查询的页访问；
  - 执行 ms：Database.execute 端到端（编译 + 执行 + 刷新 + 事务日志）；
  - 执行器 ms：仅执行器执行优化计划的耗时；
  - 峰值内存：tracemalloc 峰值（执行器路径）。
- 数据：单表 t(id INT, name VARCHAR)，行 (i, 'vi')，i = 0..N-1。

## 规模、过滤与冷/热缓存

| 规模 | 查询 | 扫描行 | 结果行 | 冷:缺失 | 热:缺失/命中 | 执行器 ms | 峰值内存 |
|---|---|---|---|---|---|---|---|
| 100 | SELECT * | 100 | 100 | 2 | 0 / 1 | 0.41 | 42.1 KiB |
| 100 | WHERE id = 1 | 100 | 1 | 2 | 0 / 1 | 0.31 | — |
| 100 | WHERE id < 10 | 100 | 10 | 2 | 0 / 1 | 0.45 | — |
| 1000 | SELECT * | 1000 | 1000 | 6 | 0 / 5 | 3.47 | 271.8 KiB |
| 1000 | WHERE id = 1 | 1000 | 1 | 6 | 0 / 5 | 3.01 | — |
| 1000 | WHERE id < 100 | 1000 | 100 | 6 | 0 / 5 | 4.89 | — |
| 10000 | SELECT * | 10000 | 10000 | 50 | 0 / 49 | 55.28 | 3132.8 KiB |
| 10000 | WHERE id = 1 | 10000 | 1 | 50 | 0 / 49 | 61.61 | — |
| 10000 | WHERE id < 1000 | 10000 | 1000 | 50 | 0 / 49 | 54.54 | — |

观察：

1. 扫描行始终等于全表行数：Filter 在 SeqScan 之上逐行判断，不减少存储扫描量。
2. 执行器耗时随规模线性增长（0.4ms → 3.5ms → 55ms，每 10 倍规模约 10 倍），
   无超线性迹象；峰值内存 10k 行全表结果约 3.1 MiB。
3. 同一显式事务内第二次执行相同查询缺失为 0、全部命中，热缓存只省页读取
   （磁盘页读取被缓存吸收），执行器计算量不变。

## 事务边界

| 规模 | 方式 | 端到端 ms | 口径说明 |
|---|---|---|---|
| 100 | 自动提交 SELECT * | 12.3 | 含整库前映像日志复制、提交标记与刷新 |
| 100 | BEGIN + SELECT * + ROLLBACK | 36.2 | 含日志复制 + 查询 + 文件恢复，一次付清后多条查询才摊薄 |
| 1000 | 自动提交 SELECT * | 13.8 | 同上 |
| 1000 | BEGIN + SELECT * + ROLLBACK | 37.1 | 同上 |
| 10000 | 自动提交 SELECT * | 69.6 | 日志随库文件增大 |
| 10000 | BEGIN + SELECT * + ROLLBACK | 91.9 | 同上 |

结论：**用户表扫描与事务整库日志是两本账**。WHERE 恒真/恒假优化减少的是前者
（扫描行、执行器耗时），自动提交下每条 SELECT 仍要为整库前映像日志付费；把
“扫描减少”等同于“整体提速”是错误的统计口径。

## 批量加载与多语句执行成本

| 方式 | 1000 行 | 10000 行 | 复杂度 |
|---|---|---|---|
| 单次 execute 批量 1000 条 INSERT（显式事务内） | 41.8 s | 未测（分钟级） | O(N²) |
| 分块 execute（每块 100 条） | 2.4 s | 47.2 s | O(N×块大小) |
| 显式事务内逐条 execute（日志只付一次） | 0.27 s | 2.54 s | O(N) |

批量多语句的 O(N²) 来源：为保留文件级行列位置，`split_statements` 给每个片段
填充此前语句的等长空白前缀，第 k 个片段的词法扫描量约为 k×语句长度；N 条语句
合计 O(N²)。这是位置保留约定的架构代价，不是缺陷，但批量加载应使用
「显式事务内逐条 execute」（线性、日志只付一次），该策略已用于基准脚本的
`load_rows` 与示例。如后续需要支持超大脚本单次执行，可在编译器中引入带起始
偏移的词法接口（属于后续优化候选，不在本轮范围）。

## 流式化决策：保持物化收集，不改为迭代处理

- 最终结果本就需要整体收集（ExecutionResult.rows 为 tuple，CLI 表格整体输出）；
- 10k 行全表扫描的执行器耗时约 55ms、峰值内存约 3.1 MiB，物化的中间列表
  不是瓶颈，瓶颈在页读取与整库日志；
- 把 DELETE 的扫描改为边遍历边删页存在漏删/重复删风险，收益与风险不匹配。

在课程规模（万行级）下维持「先收集再过滤/投影」的物化实现；若未来数据规模
上两个数量级，再重新评估迭代执行并同步更新本决策。
